## Context

生产 CPA 主机当前以 systemd 运行 CPA：

- 服务：`cpa.service`，当前状态为 active。
- 工作目录：`/opt/cpa`。
- 启动命令：`/opt/cpa/bin/cli-proxy-api -config /opt/cpa/config.yaml`。
- 监听：`127.0.0.1:8317`；Sub2API 监听 `127.0.0.1:8080` 并转发生产请求。
- 当前版本：CLIProxyAPI `v7.2.61`，提交 `ca67caf0`。
- 目标版本：固定为官方 `v7.2.82` 的 Linux AMD64 资产。
- 固定资产：`CLIProxyAPI_7.2.82_linux_amd64.tar.gz`。
- 固定 SHA-256：`10c588f9957257b8d322318167c14d8a8fd7aa5315c528c1ea0ddb21843b7019`。

目标版本发布于 `2026-07-17 16:17:05`（Asia/Shanghai）。由于它刚发布且本次新增内容主要涉及 plugin store、Kimi 与 xAI 图像兼容，而不是当前 Codex 主链路，生产执行不得早于发布满 24 小时，即 `2026-07-18 16:17:05`。执行时仍需复核官方 release、资产摘要和公开回归信息，但不得因出现新版本而自动改变本变更目标。

最近 24 小时的成功请求显示，生产主链路主要为：

- `gpt-5.6-sol` 的 `/v1/responses`。
- `codex-auto-review` 的 `/v1/responses`。
- `gpt-5.5` 的 `/v1/chat/completions` 与 `/v1/responses`。
- 少量 Chat Completions 到 Responses 的转换、WebSocket/compact 和自定义工具流程。

因此，验收以 Responses、自定义工具和当前生产模型为中心；用户已明确 `gpt-5.4` 过时，本变更不以修复或调整它为目标。

## Goals / Non-Goals

**Goals:**

- 将生产 CPA 二进制从 `v7.2.61` 受控升级至固定的 `v7.2.82`。
- 在切换前证明目标资产可信、平台匹配且旧版本可恢复。
- 将计划停机控制在 60 秒内，并在关键门禁失败时自动回到 `v7.2.61`。
- 通过直连 CPA 和经 Sub2API 的脱敏真实案例证明现网主要合同没有回归。
- 观察认证池、错误率、延迟、模型目录和工具调用在立即、15 分钟及 24 小时三个窗口内的表现。

**Non-Goals:**

- 不升级或重启 Sub2API、Nginx、数据库及其他服务。
- 不修改 `config.yaml`、systemd unit、账号池、模型映射、日志策略、`-local-model` 参数或认证策略。
- 不处理 `gpt-5.4` 的可用性、性能或映射问题。
- 不迁移 OAuth 数据，不在正常回滚时恢复旧 OAuth 快照。
- 不自动跟随 `v7.2.83` 或之后版本；目标变化必须另行确认。

## Decisions

### 1. 使用固定版本与发布龄门禁

本变更固定 `v7.2.82`、Linux AMD64 资产及其 SHA-256，并要求至少 24 小时公开观察期。执行时若官方摘要不一致、资产被撤回、出现高严重度回归，或目标版本不是已批准的固定版本，停止执行并请求确认。

替代方案是始终安装执行时的 latest。该方案不可复现，也会使审查过的差异和实际部署版本不一致，因此不采用。

### 2. 只替换 CPA 二进制

切换仅触及 `/opt/cpa/bin/cli-proxy-api`。配置、service unit、Sub2API 和路由保持原状，使问题面只包含上游二进制版本变化。

替代方案是同时增加 `-local-model`、修改日志或清理模型映射。该方案无法区分二进制升级与配置变化造成的影响，因此不纳入本次升级。

### 3. 不运行共享 OAuth 目录的并行 canary

候选二进制只做离线的架构、摘要和版本检查，不以第二实例连接现有 OAuth 目录。生产验证在短暂停机切换后进行。

并行 canary 虽能减少切换风险，但两个 CLIProxyAPI 实例共享认证目录时可能并发刷新或改写 OAuth 状态，风险高于短暂停机。

### 4. 二进制优先回滚，OAuth 快照仅用于灾难恢复

升级前解析实际 `ExecStart` 二进制路径和 `config.yaml` 中的认证目录，备份当前二进制、配置、完整 unit/drop-in/EnvironmentFile 元数据。OAuth 目录快照在旧服务完全停止后、替换二进制前创建，使用 root-only 目录保存所有者、模式、ACL/xattr 和不回显文件内容的校验清单。正常回滚只恢复 `v7.2.61` 二进制并重启服务；只有证明确有认证数据损坏并再次评审后，才允许恢复 OAuth 快照。

直接恢复旧 OAuth 快照可能覆盖升级窗口内已经刷新的 Token，因此不能作为默认回滚步骤。

### 5. 采用三层验收和稳定信号对比

验收分为：

1. 进程层：systemd、版本、监听、启动日志。
2. CPA 直连层：认证后的模型目录与最小 Responses 请求。
3. 生产链路层：经 Sub2API 和公网入口回放生产主流请求。

每个真实案例只比较稳定信号：HTTP/流式结束状态、响应类型、模型、文本非空、工具名、`call_id`、工具参数可解析和错误分类；不要求自然语言逐字相同，不记录凭据或完整敏感请求体。

### 6. 将版本跨越中的行为差异设为显式门禁

`v7.2.61` 到 `v7.2.82` 的关键风险按以下方式处理：

- `ultra` 推理档位：升级前统计是否仍有真实请求使用；若有，必须加入前后同请求验证，失败即阻断或回滚。
- 运行时 Codex 模型目录刷新：升级前后导出脱敏模型 ID 集合，任何生产在用模型消失均视为失败；本次不通过增加 `-local-model` 掩盖差异。
- OAuth 重构：切换前确认无进行中的登录/device flow，并核对有可调度认证账号；切换后监控 `invalid_grant`、无可用账号及刷新失败。
- 错误请求体记录增强：升级前确认日志目录权限、剩余空间和保留策略；验收只使用脱敏摘要，不扩大 debug 或请求日志范围。

## Risks / Trade-offs

- [目标版本刚发布，缺少充分生产样本] → 至少等待 24 小时并复核官方 release、资产摘要和公开高严重度回归；门禁不通过则停止。
- [systemd 切换造成短暂请求失败] → 选择低流量窗口，先完成全部离线检查，停服后执行同文件系统原子替换，将计划停机限制为 60 秒。
- [模型目录动态刷新导致模型消失或属性变化] → 保存升级前脱敏模型列表和近 24 小时在用模型集，升级后做集合差异；在用模型缺失立即回滚。
- [自定义工具、namespace 或 `call_id` 行为改变] → 用真实结构的 Responses 自定义工具案例比较稳定字段，并要求连续通过。
- [OAuth 刷新状态发生变化] → 切换前排除进行中的 OAuth 操作，不并行运行候选实例，正常回滚不覆盖已推进的 Token 状态。
- [错误日志可能包含更完整的请求信息] → 不启用 debug，不输出日志原文，只检查错误类别、数量、文件权限与磁盘增量。
- [回滚备份本身不可执行] → 切换前校验备份哈希、所有者、权限和版本输出，并准备完整回滚命令。
- [只升级二进制会保留既有配置缺陷] → 这是为了缩小变更面；发现配置问题时单独立项，不在本窗口混改。

## Migration Plan

### 阶段 0：发布门禁

1. 等待至 `2026-07-18 16:17:05`（Asia/Shanghai）之后。
2. 复核官方 `v7.2.82` release 仍存在，Linux AMD64 资产名和 SHA-256 与本设计一致。
3. 检查是否存在官方撤回、严重回归或与 Responses、OAuth、自定义工具相关的阻断问题。
4. 如出现新版本，只记录，不改变目标；如确需改目标，停止并重新确认计划。

### 阶段 1：生产基线

1. 记录 UTC 时间、主机架构、磁盘空间、`cpa.service` 状态、启动命令、当前版本和 `8317/8080` 监听。
2. 记录最近 15 分钟 CPA/转发链的请求量、5xx、认证错误、P95 总时长和 P95 TTFT，排除已明确不在范围内的 `gpt-5.4`。
3. 导出脱敏的当前模型 ID 集合与最近 24 小时生产在用模型集合。
4. 检查是否有 `ultra`、WebSocket/compact、自定义工具和进行中的 OAuth 流程；有真实使用的路径必须加入验收矩阵。
5. 记录升级前的代表性结果：
   - CPA 直连 `gpt-5.6-sol /v1/responses`。
   - Sub2API `gpt-5.6-sol /v1/responses`。
   - Sub2API `codex-auto-review /v1/responses`。
   - Sub2API `gpt-5.5 /v1/responses`。
   - Sub2API `gpt-5.5 /v1/chat/completions`。
   - 公网入口 `gpt-5.6-sol /v1/responses`。
   - 自定义工具/namespace 与实际使用的附加路径。

### 阶段 2：备份与候选准备

1. 解析 `ExecStart` 实际二进制路径、`readlink -f` 结果、文件系统和 `config.yaml` 中的认证目录；创建 `/opt/cpa/backups/cpa-v7.2.61-<UTC>/`，保存当前二进制、配置副本、`systemctl cat` 涉及的 unit/drop-in、EnvironmentFile 元数据和文件哈希。
2. 预创建 root-only 的认证快照目标和命令；实际快照必须在旧服务完全停止后执行，仅作为灾难恢复材料，证据中不得输出认证文件名或内容。
3. 验证备份二进制的版本、所有者、`0755` 权限和 SHA-256，并将回滚源固定为该备份二进制、目标固定为解析后的 `ExecStart` 实际路径。候选、备份与正式路径必须位于同一文件系统。
4. 将固定资产下载至 `/opt/cpa/staging/v7.2.82/`，同时校验 GitHub asset digest 与发布的 checksums。
5. 解压后检查 `file`/架构、所有者、权限和版本输出。已知该程序的 `--version` 可能在打印版本后以状态码 2 退出，应以首行版本字符串校验，不把该状态码单独判为失败。
6. 不启动第二个共享 `/opt/cpa` 认证目录的 CPA 实例。

### 阶段 3：切换

1. 确认低流量窗口且没有进行中的 OAuth 登录/device flow，记录切换开始时间。
2. 停止 `cpa.service`，强制确认状态为 inactive、旧主 PID 已退出且 `127.0.0.1:8317` 已无监听；任一不满足即停止，不替换文件。
3. 从实际配置解析认证目录，在 root-only 备份目录中创建保持 owner/mode/ACL/xattr 的一致性快照与校验清单；正常回滚不得恢复该快照。
4. 将候选二进制安装到正式路径所在文件系统的临时路径，设为 `root:root`、`0755`，再原子重命名覆盖解析后的 `ExecStart` 实际路径。
5. 启动 `cpa.service` 并在 30 秒内检查 active、`127.0.0.1:8317` 监听和版本为 `v7.2.82`，记录切换结束时间并确认停机不超过 60 秒。
6. 服务、监听或版本任一不符合即从固定备份源原子恢复 `v7.2.61`，不继续业务回放。

### 阶段 4：立即验收

1. 检查启动日志无 panic、持续重启、认证目录权限错误或配置解析错误。
2. 认证访问 CPA `/v1/models`，与升级前集合比较；任何生产在用模型消失即回滚。
3. 依次回放基线中的直连 CPA、Sub2API 的 `gpt-5.6-sol` Responses、`codex-auto-review` Responses、`gpt-5.5` Responses、`gpt-5.5` Chat Completions、公网入口 Responses 和自定义工具案例。
4. 自定义工具案例至少验证一次工具调用和一次 tool-result continuation，确认工具名、`call_id` 和参数可解析。
5. 每个关键案例最多重试一次；同一案例连续两次失败、响应合同错误、工具参数无法解析或出现无可用账号即回滚。
6. 若基线证明存在 `ultra`、WebSocket/compact 等真实流量，完成对应前后验证后才进入观察期。

### 阶段 5：观察与判定

1. 切换后连续观察至少 15 分钟，以 usage/ops 聚合中的非 `gpt-5.4` 生产请求为分母：服务无重启、5xx 不超过 1%、`invalid_grant`/refresh failure/no available accounts 不得持续增长，关键真实案例连续成功。样本少于 20 条时延长到 30 分钟，不以小样本判定通过。
2. 使用同一数据源和时间窗与升级前比较 P95 总时长和 P95 TTFT，增幅均不得超过 20%；超出时先排除流量结构变化，否则回滚。
3. 保持 24 小时观察，检查模型目录、认证刷新、错误率、延迟、工具调用和日志磁盘增量。
4. 24 小时无阻断回归后，标记升级成功，保留 `v7.2.61` 作为唯一上一版本回滚备份；经确认后再删除更旧的 `v7.2.42` 备份。

### 回滚

触发条件包括：

- 启动后 30 秒内服务或 `8317` 监听不健康。
- 生产在用模型缺失。
- 任一关键真实案例连续两次失败。
- 自定义工具合同、`call_id` 或参数解析回归。
- 持续出现 OAuth 刷新失败、无可用账号或认证池异常。
- 5 分钟窗口 5xx 超过 1%，或同口径 P95 总时长/TTFT 增幅超过 20% 且无法由流量变化解释。

回滚步骤：

1. 停止 `cpa.service`。
2. 从备份中经版本、哈希、`root:root`、`0755` 验证的固定源，原子恢复到解析后的 `ExecStart` 实际二进制路径。
3. 启动服务，重新完成进程层、CPA 直连层和 Sub2API 生产链路层验证。
4. 配置、unit/drop-in、EnvironmentFile 和 OAuth 快照均为审计/灾难恢复材料，正常回滚不得覆盖；只有证明确有对应数据损坏、停止服务并单独评审确认后才执行。
5. 保留脱敏时间线、触发指标和稳定信号差异，用于后续重新评估。

## Open Questions

- 已解决：用户已确认低流量执行窗口、最长 60 秒停机和回滚授权。
- 若 24 小时公开观察期内出现 `v7.2.83`，默认仍执行已审查的 `v7.2.82`，除非用户批准重做版本差异与门禁。
- 只有基线确认生产确有 WebSocket/compact 或 `ultra` 请求时，才将对应案例设为强制验收；否则记录为未发现真实使用，不人为扩大测试面。
